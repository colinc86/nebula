**Stage purpose:** Validate the entire training pipeline end-to-end (small + cheap) before committing to the production run in Phase 7

## Why this run exists

Per the saved training-cost approval gate memory, paid fine-tuning jobs require a brief presented to the user with explicit approval before submission. This is the brief.

The validation run is deliberately small and cheap. Its job is to answer four questions:

1. **Format question:** Does Together AI's fine-tuning API actually accept the OpenAI-compatible multi-turn JSONL with `tool_calls` and `tool` role messages, the way the docs say it does? (Documented yes; we want to confirm with a real upload before wasting production-run money on a format mismatch.)
2. **MoE LoRA placement question:** Does our `lora_trainable_modules` override actually exclude the router, and does Together honor it? (Critical for MoE stability — covered in research, but no community report exists for Qwen3-Coder-30B-A3B specifically on Together.)
3. **Pipeline question:** Can we actually pull the merged checkpoint, convert to GGUF, deploy to Ollama, and run it through `host_agent_runner.py`? (No part of this has been exercised end-to-end before.)
4. **Capability question (G3 gate):** Does the validation-trained model show ≥10% improvement over stock on at least one Phase 1 metric (token cost, pass rate, or turn count)?

If any of those four answers comes back wrong, **we stop and debug** before spending the production budget.

## Training schedule

| | | Rationale |
|---|---|---|
| `learning_rate` | **5e-5** | Smaller than the existing 7B LoRA's 1e-5 per token, but the model has more params; this is the conservative middle of community-reported ranges for Qwen3-Coder LoRA. |
| `batch_size` | **2** | Together caps Qwen3-Coder-30B-A3B at batch_size=2; we got an explicit error trying batch_size=4. |
| `n_epochs` | **2** | Validation pass — production gets 3 |
| `warmup_ratio` | **0.05** | Standard |
| `seq_length` | **8192** | Covers our agent traces (typical trace ≤4K tokens, max ≤7K). Longer would waste cost on padding. |

## What happens if approved

1. `train_validation.py --data data/validation_train.jsonl --confirm` uploads the JSONL via `client.files.upload(purpose="fine-tune")`.
2. Submits the job via `client.fine_tuning.create(...)` with the parameters above.
3. Saves job metadata to `phase4_job.json`.
4. Polls via `python3 ../train.py --status JOB_ID` until completion.
5. Downloads the merged checkpoint via `client.fine_tuning.content(ft_id=JOB_ID, checkpoint='merged')`.
6. Phase 5 begins: GGUF conversion → ollama deploy → Phase 1 re-run for the G3 gate comparison.

## What happens if denied or paused

The script defaults to dry-run. Without `--confirm`, nothing happens — no API spend. You can re-run the brief any number of times. Tweak the hyperparameters in `train_validation.py` constants and re-run.

## What we learned during submission (issues hit + fixed)

| | Issue | Fix |
|---|---|---|
| 1 | `together` SDK not installed in `.venv` (the venv was carried over from the old Linux box and binary-incompatible with macOS ARM64) | Recreated `.venv` cleanly, installed `together==2.7.0` |

| 3 | Together upload validator: `Found extra column "_task_id"` | Added `sanitize_for_upload()` that strips `_task_*` and `_wall_seconds` metadata into a temp file before upload, leaves the original intact |
| 4 | `Requested batch size of 4 is higher than the maximum allowed value of 2` for this model | Bumped down to `batch_size=2` |
| 5 | `cannot find gate_proj in LoRA-trainable modules` for Qwen3-Coder-30B-A3B | Together's API doesn't recognize HF FFN module names for this MoE. Fell back to attention-only (`q_proj,k_proj,v_proj,o_proj`). Open question for Phase 6: ask Together support for the correct FFN module names. |

These all surfaced in the first 10 minutes of submission attempts and cost $0 in API spend. Exactly the "no oops" we wanted — the validation run is supposed to surface format/parameter issues cheaply BEFORE the production run, and it did.
